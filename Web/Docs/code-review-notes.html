Reading Interchained

A code review of the gameplay loop, written for one developer. Architecture and code quality, kept separate. Patterns and heuristics, not commandments.

1. How to read this

This is a review of the Interchained gameplay loop, written for one developer who is also the project's only reader. The goal is not to score the code — it is to surface patterns worth keeping, habits worth gently nudging, and a small handful of refactors that each teach a useful idea.

Two reviews happened in parallel. One looked at the architecture: how the game is organised, where logic lives, what would be hard to extend. The other looked at the code quality: names, duplication, method shape. They are deliberately kept separate. A codebase can be cleanly written inside a broken architecture, and vice versa; mixing the two critiques muddies both.

Throughout, we lean on Martin Fowler's code smells (from chapter 3 of Refactoring). A smell is a heuristic — a labelled hint that something might be worth a second look. It is never a hard rule. The bar for acting on a smell is: does this actually hurt readability or maintainability, here, in this small project? If not, leave it.

Project context Interchained is a Unity puzzle game with one beginner developer. It is a learning environment first, a shipped product second. Every recommendation here has to clear the “doesn't overcomplicate” bar. No frameworks, no enterprise patterns, no abstractions for their own sake.

2. What's already working

Before any review, it helps to name what is working. These patterns are the project's strengths, and new code should build on them rather than around them.

  • The Validator is a clean read-only query layer. It takes a HexGrid, returns IEnumerable<TileData>, mutates nothing gameplay-facing. This is the project's strongest seam, and the right place to add the planned gear-loop meshing rule.
  • Tile view components subscribe reactively via UnityEvents. TileVisuals listens to onValueChanged and onLoopChanged, then re-renders itself. The orchestrator never tells the view to update. This is the template every new view behaviour should follow.
  • ScriptableObject config drives BoardColors, TileLabels, and Levels. Data stays out of code, palettes can be tweaked without recompiles. The foundation for a real editor flow is already there.
  • HexGrid is the single source of location truth. It owns the tile array and the regions; nothing else keeps its own index. O(1) GetTile. Don't break this.

3. Architecture observations

Ten findings. Each one names a place where the code resists change, and points at the smallest first move that would unblock it. Tags show which future feature each one touches: [editor] [modes] [mechanics] [tutorial].

3.1 Interchained is a god-class (~744 lines)

The orchestrator MonoBehaviour owns input handling, the evaluation cycle, pair-assignment scoring (~170 lines of CheckForPair/ScorePair logic at Interchained.cs:376), loop validation dispatch, save/load orchestration, label toggling, and debug drawing. Nearly every future feature lands in this one file. First move: extract a PairAssigner — it's the most self-contained chunk and clears room for everything else. [editor] [modes] [mechanics]

3.2 TileData derives its identity from the transform

TileData extends Node, and Node.cs:15 derives hex from transform.position. So a tile's logical identity depends on its view transform. The class also carries UnityEvents and a ParticleSystem SerializeField. Hidden tiles, animations, or headless tests all fight the transform coupling. First move: keep it a MonoBehaviour (converting to a POCO isn't worth it for one beginner), but stop deriving hex from the transform — store axial coords as a serialised field set at instantiation. [mechanics] [tutorial]

3.3 Two sources of truth for tile validity

invalidTiles (the HashSet) and each tile's IsInvalid flag are updated together but can drift. For instance, ClearTile sets IsInvalid = false but leaves the tile in the set until the next ReevaluateInvalidTiles. First move: pick one as the truth. Either make IsInvalid the only state and derive the set by scan, or route every mutation through MarkAsInvalid/MarkAsValid so set membership stays in lockstep. [modes]

3.4 Pair logic has no home

Interchained.cs:356 manipulates pairs by directly calling RemovePair/SetPairedTile across two tiles, and the scoring heuristics live as a local function inside the orchestrator. Pair rules are a gameplay mechanic with nowhere to live, so they accrete orchestrator code. First move: move CheckForPair/ScorePair into a PairAssigner class that takes the grid; TileData keeps only the pair-link primitives. [mechanics]

3.5 Bit-packed save format has no owner

The save format is documented in SaveLoad.cs:20, encoded in SaveLoad.ToBoardData1D, and decoded in HexGrid.SetBoard:157. Adding a new flag (say, hidden tiles — bit 8 is already reserved but commented out) touches all three. First move: centralise encode/decode as TileData.Encode()/Decode(int) so the format lives next to the state it describes. [editor] [mechanics]

3.6 LoopNode.IsValid has a logic bug

See section 5. Short version: the operator is wrong, so the validity gate doesn't gate anything. [mechanics] [modes]

3.7 LoopDrawer owns state it shouldn't

LoopDrawer constructs its own Validator (separate from the orchestrator's), stores a stale possibleLoopTiles array across calls, and writes to TileData.LoopIn/LoopOut directly via public fields. As the loop subsystem is re-enabled, these become drift surfaces. First move: inject the shared Validator, clear possibleLoopTiles at the top of SortLoopTiles, encapsulate LoopIn/LoopOut behind setters (see refactor #3). [mechanics]

3.8 The win condition is hardcoded with no seam

IsSolved() at Interchained.cs:643 is just invalidTiles.Count == 0. AGENTS.md correctly identifies that the canonical check is “the loop is closed”. New game modes — different win conditions — have nowhere to plug in. First move: a one-method IWinCondition interface (or even a Func<HexGrid, LoopGraph, bool>) field on Interchained, swapped per mode. A strategy seam, not a framework. [modes]

3.9 GameManager is an underused singleton

GameManager has WaitingToStart/GamePlaying/GameOver states, but GameOver is commented out, and the only consumer is Interchained.cs:67's IsGamePlaying() gate. This is the natural home for mode wiring and the win→celebration transition. First move: route win detection through GameManager (it already has OnStateChanged), making it the single state owner. [modes]

3.10 Input is read inline

AcceptInput at Interchained.cs:65 polls Input.* directly. A tutorial that wants to gate, replay, or scripted-feed input has no seam; same for an undo system. First move: a tiny InputActions struct (CycleUp/CycleDown/Set/MarkLoop/Clear) populated from Input now, swappable later. Not a full command system — just a seam. [tutorial]

4. Code quality observations

4.1 The style guide, as inferred from the code

The project does not have a written style guide, but it does have habits. Reading the gameplay loop, these conventions show up consistently enough to treat as the de-facto baseline:

  • Private fields: inconsistent. Underscore prefix for “service” dependencies (_validator, _loopDrawer, _hexGrid), no prefix for state (invalidTiles, hexGrid, possibleLoopTiles). Public inspector fields are unprefixed.
  • Naming: PascalCase for public methods and properties; camelCase for locals and parameters; type names PascalCase. UnityEvent fields use onXxx.
  • Validator query idiom: IEnumerable<TileData> lazy-yielding offending tiles, used both as a boolean (.Count() != 0) and as a list. This is the project's central validation pattern.
  • State mutation: through Mark*(value) methods on TileData, which fire onValueChanged/onLoopChanged. Direct field writes are reserved for MarkBlocker/ClearTile internals.
  • Unity inspector: [SerializeField] private for dependencies, public for things wired in the inspector. #if UNITY_EDITOR guards gizmos.
  • Organisation: #region blocks group the orchestrator by responsibility.
  • Domain values: int Value discriminated via boolean properties (IsEmpty/IsNumber/IsGear/IsBlocker); modern C# pattern matching (is 8 or 9).

4.2 Smell findings (brief)

Each smell below has at least one genuine instance in the gameplay loop. Full quotes and code samples appear in the refactor sections where relevant; the rest are signposts for your own reading.

Mysterious Name — SortLoopTiles doesn't sort (LoopDrawer.cs:41); EvaluateLoopTiles has a caching side effect (LoopDrawer.cs:26); msg controls debug output and is always true (Interchained.cs:376, 534); PassesPlacementEval is a PascalCase local that's still loop-rechecked (Interchained.cs:254); FindInAdjacent reads backwards (Validator.cs:142). See refactor #2.

Duplicated Code — LoadBoardState vs LoadClipboard are ~95% identical (Interchained.cs:660); the number vs gear branches of ValidatePlacement share a shape (Interchained.cs:312); IsDuplicatedAlongAxis / IsDuplicatedInRegion share a count-and-yield-self shape (Validator.cs:37). See refactor #1.

Feature Envy — AssignPairs/CheckForPair (Interchained.cs:342) reads tile.IsMarkedForLoop, tile.pairedTile, tile.IsInvalid, mutates pairs through three TileData methods, and scores tile-to-tile relationships via a nested local function. The orchestrator envies TileData's data.

Primitive Obsession — int Value on TileData packs five domain concepts (empty / domino 1–6 / solo 7 / gears 8–9 / blocker 10); all consumers re-derive kind via Is* switches. Plus magic sentinels bestScore = -99 / lowestOtherScore = 99 (Interchained.cs:404, 456) and the repeated cast (int)region - 1 (Validator.cs:65).

Repeated Switches — the IsNumber/IsGear/IsBlocker dispatch cascade recurs in ReevaluateInvalidTiles, ValidatePlacement, and ValidateIsOnLoop. Each re-implements “find offenders + flag”. (Don't reach for polymorphism here — overkill for this project. See refactor #1.)

Divergent Change — Interchained.cs is edited for unrelated reasons: input, evaluation, save/load, label toggling, gizmos. Also HexGrid.cs mixes grid storage, region storage, bit-packing decode, and debug text — plus DebugUtils is defined at the bottom of the same file.

Speculative Generality — LoopGraph.FindPathDFS / FindPathBFS / HasCycle (LoopGraph.cs:117) are NotImplementedException stubs; Link.IsDirectional/FlipDirection are built but never used with isDirectional = true; BiasCone's width param is documented as TODO (Hex.cs:116); the four named region fields _regionNorth/East/South/West are only ever read via the Regions[] array.

Middle Man — HexGrid.GetGridArray() exposes the private array, defeating the GetTile() indirection. Callers (CheckBoard, ToggleTileLabels) reach in directly and re-implement iteration. Two parallel access paths.

Notable absentees: Shotgun Surgery (changes are mostly local), Message Chains (no long a.b().c().d() walks), Refused Bequest (no subclass rejecting its parent), Data Clumps (parameters are mostly single tiles or self-contained).

5. One bug worth fixing today

Tucked into LoopNode.cs:10 is a one-line bug that silently undermines a load-bearing check:

LoopNode.cs — current 
public bool IsValid
{
    get { return (Links.Count <= 2 || Links.Count >= 1); }
}

The intent is plainly “a valid loop node has 1 or 2 links”. But <= 2 OR >= 1 is true for every integer. Zero links: 0 <= 2 is true. Five links: 5 >= 1 is true. The gate never trips.

LoopNode.cs — fix 
public bool IsValid
{
    get { return Links.Count >= 1 && Links.Count <= 2; }
}
Why this matters LoopGraph.IsValid() is built on this property. With the bug, the whole graph-validity check passes no matter what — which means the planned gear-loop meshing rule and the canonical “loop is closed” win condition would silently accept any shape. Fix the operator, and the rest of the loop subsystem has solid ground to stand on.

6. Refactor #1 — Extract the shared shape

Smells addressed: Duplicated Code, Repeated Switches. Risk: very low. Behaviour change: none.

The most common smell in the gameplay loop is also the most fundamental: the same shape of code, written twice. Two places stand out.

6.1 The two load paths

LoadBoardState and LoadClipboard are nearly identical. Below, the blue lines are the shape they share; the red lines are the only thing that differs (where the board data comes from).

LoadBoardState (Interchained.cs:660)

Debug.Log($"Loading {name}");
var boardState = saveLoadHandler.LoadLevel(name);
if (boardState == null)
{
    Debug.Log("BAD BOARD STATE ABOORT");
    return;
}
ClearGameState();
hexGrid.SetBoard(boardState);
puzzleInfoField.text = "<b>" + boardState.Name
    + "</b>\n" + boardState.Description;
CheckBoard();
onLevelLoaded.Invoke();

LoadClipboard (Interchained.cs:683)

var boardState = saveLoadHandler.PasteFromClipboard();
if (boardState == null)
{
    Debug.Log("BAD BOARD STATE ABOORT");
    return;
}
ClearGameState();
hexGrid.SetBoard(boardState);
puzzleInfoField.text = "<b>" + boardState.Name
    + "</b>\n" + boardState.Description;
CheckBoard();
onLevelLoaded.Invoke();

Almost every line is shared. The fix is the simplest move in refactoring: name the shape, then call it from both places.

After — one helper, two one-line callers 
private void ApplyBoardState(BoardData1D<int> boardState)
{
    if (boardState == null)
    {
        Debug.Log("BAD BOARD STATE");
        return;
    }
    ClearGameState();
    hexGrid.SetBoard(boardState);
    puzzleInfoField.text = "<b>" + boardState.Name
        + "</b>\n" + boardState.Description;
    CheckBoard();
    onLevelLoaded.Invoke();
}

public void LoadBoardState(string name = "")
{
    Debug.Log($"Loading {name}");
    ApplyBoardState(saveLoadHandler.LoadLevel(name));
}

public void LoadClipboard()
{
    ApplyBoardState(saveLoadHandler.PasteFromClipboard());
}

6.2 The two validation branches

The same pattern shows up inside ValidatePlacement. The IsNumber branch and the IsGear branch share an identical tail — “collect offenders, mark each invalid, draw a red line, add to tracking”.

Interchained.cs:312 — the repeated tail 
var combined = axis.Union(region);
foreach (var invalidTile in combined)
{
    invalidTile.MarkAsInvalid(true);
    Debug.DrawLine(tile.hex.ToWorld(), invalidTile.hex.ToWorld(), Color.red, 1f);
    invalidTiles.Add(invalidTile);
}
// ...and the same shape again, verbatim, in the IsGear branch
After — one FlagOffendingTiles helper 
private void FlagOffendingTiles(TileData source, IEnumerable<TileData> offenders)
{
    foreach (var offender in offenders)
    {
        offender.MarkAsInvalid(true);
        Debug.DrawLine(source.hex.ToWorld(), offender.hex.ToWorld(), Color.red, 1f);
        invalidTiles.Add(offender);
    }
}

Each branch of ValidatePlacement now ends with one line: FlagOffendingTiles(tile, axis.Union(region)); for numbers, FlagOffendingTiles(tile, neighbours.Union(region)); for gears.

Lesson The most fundamental refactoring move is naming the shape. When you see two blocks of code that look the same, the right question is not “how do I make them shorter?” but “what is this for?” Once you can name it (ApplyBoardState, FlagOffendingTiles), you can call it. The code gets shorter as a side effect — the real win is that the reader now sees intent.

7. Refactor #2 — Rename to match behaviour

Smell addressed: Mysterious Name. Risk: none (pure renames). Behaviour change: none.

A function whose name resists being honest usually sits in the wrong place, or does too much, or has a side effect it shouldn't. The diagnostic question is simple: if you told a teammate this name, would they guess correctly what the function does?

Lesson Renaming is the cheapest refactor with the highest readability payoff. When a name resists being honest — when no truthful verb-noun pair comes to mind — that's a signal, not a vocabulary problem. It usually means the function is doing two things, or sitting on the wrong class, or carrying a side effect. The murky name is the design trying to tell you something.

8. Refactor #3 — Encapsulate TileData loop state

Smells addressed: Feature Envy (in reverse), coupling risk. Risk: low. Behaviour change: events fire correctly where they currently don't.

Five loop-related fields live directly on TileData:

TileData.cs:27 — public mutable fields 
public LoopNode LoopNode { get; private set; }
public bool IsMarkedForLoop { get; private set; }
public TileData LoopIn;     // <-- public mutable
public TileData LoopOut;    // <-- public mutable
public bool IsOnLoopIncorrectly { get; private set; }

The two problem children are LoopIn and LoopOut. They're public mutable fields, written directly by LoopDrawer.TryToDrawLoop:

LoopDrawer.cs:90 — orchestrator mutates model internals 
tileData.LoopIn = adjacentSteps[0];
tileData.LoopOut = adjacentSteps[1];
// ...later...
adjacentTile.LoopIn = tileData;

This is a coupling problem with three teeth:

  1. No invariant is enforced. LoopIn and LoopOut are meant to come in pairs, but nothing stops one from being set without the other.
  2. No event fires. The other three loop fields trigger onLoopChanged when they change. LoopIn/LoopOut silently don't, so view components can't react.
  3. Ownership is ambiguous. TileData stores the state, but LoopDrawer owns its meaning. If a third writer ever appears, they will collide.

Option A: encapsulate behind a setter (do this now)

TileData.cs — private fields + setter that fires events 
private TileData loopIn;
private TileData loopOut;

public TileData LoopIn  => loopIn;
public TileData LoopOut => loopOut;

public void SetLoopEndpoints(TileData in, TileData @out)
{
    loopIn = in;
    loopOut = @out;
    onValueChanged.Invoke();
    if (IsMarkedForLoop) onLoopChanged.Invoke();
}

public void ClearLoopEndpoints()
{
    loopIn = null;
    loopOut = null;
}

LoopDrawer now calls tileData.SetLoopEndpoints(a, b) instead of writing the fields directly. Events fire. The pair invariant has a single chokepoint. The change is mechanical and quick.

Option B: bundle into a LoopMembership value (defer)

Once the gear-loop meshing rule lands, the five loop fields will start wanting to travel together — passed to validators, inspected by win conditions, serialised. At that point, bundling them into a small LoopMembership value type starts to pay for itself:

Sketch — not for today, for when the gear-loop rule lands 
// A small value type that owns all loop-related state together.
public class LoopMembership
{
    public bool IsMarked;
    public TileData LoopIn;
    public TileData LoopOut;
    public bool IsIncorrect;
    // plus the methods that mutate them, in one place
}

This is a Data Clump waiting to be born — and giving it a name early keeps the orchestrator thin.

Lesson Encapsulation is not about purity. It's about making invalid state impossible to express. With public mutable fields, LoopIn can be set to a tile on the far side of the board while LoopOut is null, and nothing in the code stops you. With a setter, the rule “endpoints come as a pair and fire an event” lives in exactly one place — and any future bug has to go through that place to be born.

9. Where to go next

Difficult areas

  • Pair-assignment scoring (CheckForPair/ScorePair, Interchained.cs:361). Dense, partially commented out, magic sentinels, no home on the data it operates over. Read it twice before changing anything.
  • The loop subsystem in flux. LoopDrawer + LoopGraph + TileData.LoopIn/LoopOut are mid-rewrite. Direction assignment is unreliable, the LineRenderer walk is disabled, and LoopNode.IsValid is broken (section 5). Fix the bug first; stabilise direction second; only then re-enable TryToDrawLoop.

Ripe for refactor

The three refactors in this doc, in order of value-for-effort:

  1. Extract ApplyBoardState + FlagOffendingTiles (section 6) — kills the most visible duplication, shrinks the god-class, zero behaviour change. An afternoon.
  2. Rename to match behaviour (section 7) — pure renames, immediate readability gain, aligns code with what AGENTS.md already calls these concepts.
  3. Encapsulate TileData loop state (section 8) — the biggest coupling risk heading into gear-loop meshing. Option A now, option B when that rule lands.

Good opportunities to learn

  • Naming as design pressure. The Mysterious Name findings are perfect mini-lessons. When a name resists being honest, the design is usually murky — fix the name and you often find the right shape.
  • Single Responsibility in the small. Carving SaveLoad orchestration and LabelToggle out of Interchained teaches Divergent Change viscerally — you can feel the relief of a file that changes for one reason.
  • Strategy pattern in miniature. An IWinCondition interface with one method is the most beginner-friendly introduction to polymorphism-as-seam. One method, one interface, swapped per game mode. Serves the future “different game modes” work without dragging in a framework.
  • Encapsulation discipline. Making LoopIn/LoopOut private teaches why public mutable fields are a coupling liability. The lesson pays off before the gear-loop meshing work lands.

10. Glossary

Terms used in this review, grouped by theme. Where a term has a glossary entry, the first use in the body of the review links here.

Architecture & object-oriented design
Architecture
The high-level shape of a codebase: which modules exist, what each one is responsible for, and which way the dependencies flow. “Good architecture” mostly means changes stay local — one feature touches one place. See also: coupling, cohesion, SRP.
Pattern (design pattern)
A named, reusable solution shape for a recurring design problem. Patterns are vocabulary more than recipes — once you can say “Strategy pattern”, you and your teammate can discuss a design in one word instead of ten. Use sparingly; not every problem needs a pattern.
God-class (god object)
A class that knows about or does too much. Tends to grow indefinitely because every new feature finds a reason to live there. Interchained.cs is on this path at ~744 lines. See also: SRP, divergent change.
Cohesion
How tightly a class's contents belong together. High cohesion: everything in the class serves one purpose. Low cohesion: the class is a junk drawer. Opposite of: coupling.
Coupling
How much one module knows about another's internals or depends on its details. Tightly coupled modules change together, whether you want them to or not. See also: feature envy, message chains.
Encapsulation
Hiding a module's internal state behind a small, intentional interface. The point isn't purity — it's making invalid state impossible to express. If a field is public and mutable, any rule about it (“must come in a pair”, “must fire an event”) is unenforceable.
Single Responsibility Principle (SRP)
A class should change for one reason. If you find yourself editing the same file for input handling, save/load, and label toggling, the file has more than one responsibility. Smell counterpart: divergent change.
Single source of truth
One canonical place where a given piece of state lives. Everywhere else, that state is either read-only or derived. When two places each hold the truth, they drift; debugging the resulting inconsistency is miserable. See also: encapsulation.
Model–View–Controller (MVC)
An architectural pattern that separates state (model), display (view), and input handling (controller). Interchained already follows this loosely: TileData is the model, TileVisuals is the view, Interchained is the controller. The view subscribes to the model via events — that's MVC done right.
Strategy pattern
Define a small interface for one piece of behaviour, then swap implementations. IWinCondition with a single IsSatisfied(...) method is a strategy: a “loop closed” mode plugs in one implementation, a “fill the board” mode plugs in another. The orchestrator doesn't change. See also: polymorphism, seam.
Polymorphism
The ability for different types to be treated as the same type at a calling site, each behaving differently. In C#, usually via interfaces or inheritance. Powerful, but easily overused — for a small project, an if/switch is often clearer than a type hierarchy.
Seam
A place in the code where you can change behaviour without editing the code that uses it. IWinCondition is a seam — new win conditions slot in without touching Interchained. Adding seams before you need them is usually over-engineering; adding them just as a second case appears is sweet spot.
Code smells (Fowler, Refactoring ch. 3)
A smell is a labelled heuristic — a hint that something might be worth a second look. It is never a hard rule. The bar for acting is: does this actually hurt here, in this project?
Mysterious Name
A function, variable, or type whose name doesn't reveal what it does or holds. Fix: rename it. If no honest name comes, the design is murky — fix the design first.
Duplicated Code
The same logic shape appears in more than one place. Fix: extract the shared shape into a named helper, then call it from both places.
Feature Envy
A method that reaches into another object's data more than its own. Fix: move the method onto the object whose data it envies.
Data Clumps
The same few fields or parameters keep travelling together across the codebase. Fix: bundle them into one type, pass that. The clump is a type waiting to be born.
Primitive Obsession
A primitive (int, string) standing in for a domain concept that deserves its own type. Fix: give the concept a small type, or at minimum named constants for the sentinels.
Repeated Switches
The same switch or if-cascade on the same type appears in multiple places. Fix: replace with polymorphism (sometimes), or extract a shared helper that both sites call (often simpler).
Shotgun Surgery
One logical change forces scattered edits across many files. Fix: gather what changes together into one module.
Divergent Change
The mirror image: one file or module is edited for several unrelated reasons. Fix: split so each module changes for one reason. (Interchained.cs suffers from this.)
Speculative Generality
Abstraction, parameters, or hooks added for needs the spec doesn't have yet. Fix: delete it. Inline back until a real need shows. YAGNI.
Message Chains
Long a.b().c().d() navigation the caller shouldn't depend on. Fix: hide the walk behind one method on the first object.
Middle Man
A class or function that mostly just delegates onward, adding nothing. Fix: cut it; call the real target direct.
Refused Bequest
A subclass or implementer that ignores or overrides most of what it inherits. Fix: drop the inheritance, use composition instead.
C# / .NET specifics
IEnumerable / lazy evaluation
An interface for “a sequence you can iterate”. In C#, methods that yield return produce an IEnumerable lazily — values are computed only as the consumer reads them. The Validator query methods all use this: they don't allocate a list, they just promise to hand offending tiles back one at a time.
HashSet<T>
A collection that cannot contain duplicates. Adding the same item twice is a no-op. Lookups, adds, and removes are O(1) on average. Used for invalidTiles precisely because a tile should either be in the set or not — never in twice.
Idempotent
An operation that can be repeated any number of times with the same result. invalidTiles.Add(t) on a HashSet is idempotent — add the same tile ten times, the set still contains it once. Useful property to design for.
Workflow
Refactoring
Changing the structure of code without changing its behaviour. The aim is to make the next change easier. Done in small, behaviour-preserving steps, each one verifiable. Fowler's book of the same name is the canonical reference.
YAGNI (You Aren't Gonna Need It)
An XP principle: don't build something because you might need it later. Build it when you actually need it. Closely allied with the Speculative Generality smell.
